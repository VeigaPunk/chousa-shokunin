## Answers to the three questions

**(1) Derivation.** Expectations are `date(year,2,28)+timedelta(1)` and `as-of > due` in Python. No gate arithmetic is reused, so the expectation is independent. Limits: `as-of` is set equal to `due`, so the freshness half is implied by the printed `due=`. The strict-overdue side is probed only at equality, which is how M5 is caught. No leap-year overdue case exists in the regression suite or in the gate's own selftest; the only `02-29` in the gate selftest is the positive 2028 case (lines 6145-6146).

**(2) Revert or mutate.** Reverting C2 (base gate, or M7 alone) leaves `leap-2028` green, because C2's hunks change no leap-relevant behavior on `1d` ASCII input. The control is not a repair detector. Its real role is guarding Feb 28→29 arithmetic at a non-century leap year, and it fails for the intended reason on arithmetic and normalization-output defects (M2, M3, M4, M5, M10).

**(3) Nearby inputs.** The landed gate is correct on every input tried: CE1 rejects Feb 29 in 1900 and 2100, CE1b marks the invalid explicit recheck unscheduled, CE2 and CE3 give the Python due. A full century sweep (every century year 100-9900: Feb 29 as as-of input and as verified-at input, 198 cases) gives 0 landed mismatches and 150 mismatches for M1 and M8 (every non-400 century). The regression block contains no invalid Feb 29 input, so the control set cannot see the century rule. The control set is vacuous for the Gregorian validator, for single-digit-cadence normalization, and for the century/era terms at 2028.

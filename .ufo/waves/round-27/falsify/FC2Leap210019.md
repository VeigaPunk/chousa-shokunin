## Verdict

**FALSIFIED (scoped).** The case's expected values are correct and independent, and it is *not* globally
vacuous: it catches a naive calendar-arithmetic leap bug. But it fails both properties the assignment asks
about:

1. It targets **no production fix** in the C2 repair. Reverting all four C2 hunks leaves it green.
2. It is **vacuous for the gate's only explicit leap rule** (`metadata_iso_date`). Removing the Gregorian
   century clause leaves `leap-2100` green *and all 21 C2 controls green*, while `--as-of 2100-02-29`
   is silently accepted (landed gate correctly exits 2). No C2 control feeds any format-valid but
   calendar-invalid date, so the entire C2 block is blind to leap-validity breakage.

The landed gate itself was not found wrong anywhere probed (540-case date grid, 0 mismatches).

## Item and mechanism

Control generated at `corpus/evidence/round27-regressions.py:108-111`:

```python
for year in (1900, 2000, 2028, 2100):
    start = date(year, 2, 28)
    due = start + timedelta(days=1)
    date_cases.append((f'leap-{year}', start.isoformat(), '1d', due.isoformat(), due.isoformat()))
```

Fixture: `verified-at = 2100-02-28`, `recheck: 1d`, `--as-of 2100-03-01` (= due). Oracle at
`round27-regressions.py:112-116` uses Python `datetime` only; expected `due=2100-03-01 freshness=current`,
exit 0. `freshness` is `asof > due ? overdue : current`, so the case also pins the strict-`>` boundary.

Production path: `verify-metadata` → `metadata_add_days` (`tools/research-gate.sh:2359-2378`), which converts
via `metadata_days_from_civil` / `metadata_civil_from_days` (`2326-2357`, Hinnant epoch-day arithmetic, **no
leap predicate by construction**). The explicit leap rule exists only in `metadata_iso_date`
(`2310-2323`, clause at 2316-2322) and is consulted only for **validity** of `--as-of`, `verified-at` and
absolute `recheck` dates — never for adding days to a valid Feb 28.

## (1) Is the expectation contract-derived and independent of gate code? — YES

Expected date and freshness come from Python `date`/`timedelta`; no gate constant or output is used.
Proleptic Gregorian: 2100 is not a leap year (2100 % 400 ≠ 0), so 2100-02-28 + 1d = 2100-03-01;
as-of == due ⇒ `current`, exit 0. The landed gate agrees:

```
$ python3 probe.py tools/research-gate.sh 2100-02-28 1d 2100-03-01   # exit=0
META entry=entry.md source=present verified_at=dated recheck=scheduled due=2100-03-01 freshness=current verdict=clean
RESEARCH_GATE: CLEAN (entries=1 complete=1 findings=0 drift=0)
```

Same for 1900 (Mar 1), 2000 and 2028 (Feb 29), all exit 0, matching Python. Persisted after-state
(`round27-regressions-after.json`) records `leap-1900/2000/2028/2100` expected 0 / actual 0 / no errors.

## (2) Revert the targeted fix → does the control fail for the intended reason? — NO

The C2 production diff consists of exactly four hunks (base `64eec5d` → target), confirmed by diffing the
whole `metadata_iso_date`/`metadata_add_days` block:
`local LC_ALL=C` in `metadata_iso_date`, `local LC_ALL=C` in `metadata_add_days`,
digit class `[0-9]` → `[0123456789]`, and extglob `${digits##+(0)}` → ERE
`^0*([123456789][0123456789]*)?$` + `BASH_REMATCH`.

Mutant **mAB** reverts all four in the sandbox copy. Result: `leap-2100` still passes unchanged.

```
$ python3 probe.py gate_mAB.sh 2100-02-28 1d 2100-03-01   # exit=0
META entry=entry.md source=present verified_at=dated recheck=scheduled due=2100-03-01 freshness=current verdict=clean
```

So `leap-2100` is a **preservation** check, not a control of the C2 repair: its inputs
(ASCII dates, cadence `1d`, locale `C`) touch none of the four hunks. For contrast, the same mAB mutant
does fail the suite's fix-sensitive locale control, so the revert is semantically real and detectable:

```
$ LC_ALL=en_US.UTF-8 gate_mAB.sh verify-metadata ... --as-of '２０２６-10-21'
rc=1; stderr: gate_mAB.sh: line 2312: 10#: invalid integer constant (error token is "10#")
             gate_mAB.sh: line 2570: 10#: invalid integer constant (error token is "10#")
$ LC_ALL=en_US.UTF-8 tools/research-gate.sh ... --as-of '２０２６-10-21'
rc=2; stderr: research-gate: --as-of must be a valid YYYY-MM-DD date
```

(Only `C`, `C.utf8`, `POSIX`, `en_US.utf8` are installed here; `en_US.utf8` really does make `[0-9]` admit
fullwidth/Arabic-Indic digits, so that control is live on this host.)

**Does the case target the date arithmetic at all?** Yes — it is sensitive to an arithmetic leap defect,
i.e. it is not globally vacuous. Mutant **mD** (defect injection, not a revert: `metadata_add_days`
reimplemented as a day walk using `year % 4` only) makes the harness predicate fail on the intended
required string, exit still 0:

```
$ python3 probe.py gate_mD.sh 2100-02-28 1d 2100-03-01   # exit=0
META ... due=2100-02-29 freshness=current verdict=clean
harness emulation: FAIL missing 'due=2100-03-01 freshness=current'   (leap-1900 likewise FAIL, due=1900-02-29)
```

Note the freshness comparison is masked there (Feb 29 maps numerically to Mar 1), so only the
required `due=` string catches mD — and it does.

## (3) Nearby input where the control is vacuous — `--as-of 2100-02-29`

Mutant **mC** changes the only leap predicate,
`year % 400 == 0 || (year % 4 == 0 && year % 100 != 0)` → `year % 4 == 0` (a one-line re-introduction of
the classic 2100 century bug in date validity). `leap-2100` stays green:

```
$ python3 probe.py gate_mC.sh 2100-02-28 1d 2100-03-01   # exit=0
META ... due=2100-03-01 freshness=current verdict=clean
```

But the same mutant accepts a nonexistent calendar date, which the landed gate rejects:

```
$ tools/research-gate.sh ... --as-of 2100-02-29                 # exit=2
  stderr: research-gate: --as-of must be a valid YYYY-MM-DD date
$ gate_mC.sh ... --as-of 2100-02-29                             # exit=0
  META ... due=2100-03-01 freshness=current verdict=clean        (silently normalized to Mar 1)
```

and an invalid absolute recheck becomes scheduled instead of unscheduled:

```
landed:  META ... recheck=unscheduled due=unknown freshness=unknown ... + FINDING META_RECHECK_UNSCHEDULED
mC:      META ... recheck=scheduled due=2100-02-29 freshness=current ...   (nonexistent date printed)
```

No C2 control supplies a format-valid but calendar-invalid date. The only date inputs in the C2 block are
`date_cases` (`round27-regressions.py:90-111`) plus the six Unicode `--as-of` tokens
(`:119-129`); the only Feb-29 inputs are 2000-02-29 and 2028-02-29, which are leap under both the correct
and the mutated rule. Empirical check with a C2-only subset driver replicating exactly those 21 cases
(`/tmp/.../mini_c2.py`, not the full suite):

```
landed         cases=21 mismatches=0   (matches persisted C2 21/21)
mC             cases=21 mismatches=0   <-- leap-predicate mutation invisible to all C2 controls
```

So `leap-2100` (and `leap-1900/2000/2028`) pins the epoch-day round trip but not the leap rule; its name
overstates coverage. The suite has **no** calendar-invalid-date control at all (not even 2026-02-30;
the gate selftest does, but at `2026-02-30`, which the century mutation still rejects).

## Limits

  there is no landed leap-arithmetic fix to revert.
- The 128 KiB zero-normalization revert was not exercised (crash class, explicitly out of bounds); the

  normalization revert was exercised with short tokens only.

- Host has no locale that admits Unicode digits other than `en_US.utf8`; the locale leg was checked there.

## Author-lane advice (not an outside admission)

- Keep `leap-1900/2000/2028/2100` (they catch naive arithmetic leap bugs), but add at least one C2 control
  for **calendar-invalid, format-valid** dates: `--as-of 2100-02-29` (and `1900-02-29`) expecting exit 2 +
  `--as-of must be a valid YYYY-MM-DD date`, and `recheck: 2100-02-29` expecting `recheck=unscheduled`.
  That closes the mutation shown here.
- Do not describe the leap cases as part of the C2-repair evidence: all four are insensitive to every C2
  hunk; the repair is carried by the Unicode-locale, 128 KiB-zero, all-zero, span and overflow cases.

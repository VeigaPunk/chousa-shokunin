# SentinelFlock32b — C1 manifest-lock review

- **Scope/verdict:** C1 design only; current gate SHA-256 matches frozen base (`sha256sum tools/research-gate.sh`, exit 0: `0bc318b3…ff11258`). No candidate or counter was run; no lane code changed; no tools installed.
- **HIGH — lock/probe/append must share one inode.** `verify_all` preflights `JSON_ARG` at `tools/research-gate.sh:3060-72`, then later reads it by pathname (`3193-95`) and reopens it for `>>` (`3199`). A path-lock followed by these path opens can be retargeted (notably an allowed symlink to a regular file), so one inode is locked while another is probed/appended; JSONL serialization and the frozen inode contract fail. **Smallest fix:** after section subprocesses and line construction, open once with append semantics, `flock -x` that FD, read the last byte through `/proc/self/fd/$fd`, write with `printf >&$fd`, then close; treat the opened inode as the manifest and keep its parent directory trusted. Benign scratch probe (exit 0) confirmed this FD/procfd read-and-append shape: `last=72`, then `prior` and `{"probe":true}`.
- **MEDIUM — special paths and TOCTOU.** The existing `-e && ! -f` check refuses a static FIFO (setup exits 2 via line 413), but follows symlinks and can race a later `>>` open; swapping a regular path for a FIFO can hang at open, before any flock timeout helps. `/dev/stdout` is especially unsafe: scratch command `bash -c '[[ -f /dev/stdout ]] ...; readlink /dev/stdout'` with stdout redirected to a regular file returned `test_f=regular` and `/proc/self/fd/1`; thus it can pass preflight. **[INFERENCE]** Appending the JSON there is followed by gate status output at lines 3205+, polluting the supposed JSONL manifest. Reject `/dev/stdout`/proc-fd pseudo-paths and verify the opened FD is regular; if an attacker can mutate the parent directory, use a nonblocking, type-checking opener or require a trusted directory.
- **MEDIUM — inherited lock FD.** `verify_all_section` spawns `bash "$SELF"` at line 3018. Linux `flock(2)` docs (`man 2 flock`, exit 0) say locks are preserved across `execve` and released only after all duplicate FDs close; Bash child inheritance was also visible in the scratch `/proc/self/fd` probe. Acquiring before section calls can let children/descendants retain the lock after the parent closes it. Acquire only after all section children finish, keep the critical section short, spawn no background work under lock, and close immediately after append.
- **MEDIUM — hostile lock holder can hang forever.** `man 1 flock` (exit 0): “By default, if the lock cannot be immediately acquired, flock waits until the lock is available”; `-w` bounds this. The frozen contract (`claims.md:23-28`) requires serialization but sets no wait deadline; the counter (`c1-count.py:23-29,67-68`) permits a 180s lock-holder phase and 300s writer deadline. Recommend `flock -x -w 300 -E 2 "$fd"`, with timeout returning **without probing or writing**; never fall back unlocked. Indefinite blocking is also contract-compatible on successful runs, but permits unbounded DoS.
- **MEDIUM — dependency and exit mapping.** This host has `/usr/bin/flock`, util-linux 2.42.4 (`command -v flock; flock --version`, exit 0); Bash FD redirection alone does not acquire `flock(2)`. Require `flock` when `--json` is used and fail closed with a diagnostic if absent. Gate contract is `0 CLEAN | 1 DRIFT | 2 setup/usage` (lines 9, 413; append failure exits 2 at 3199-3201); `flock -w` defaults to exit 1, colliding with DRIFT, and other utility errors have their own statuses. Catch all lock failures and map them to 2 (or set `-E 2` for timeout); do not let `set -e` leak an ambiguous status.
- **Filesystem limits/evidence:** `stat -f -c 'fstype=%T' /dev/shm; flock -n /dev/shm true` returned `fstype=tmpfs`, `flock_exit=0` (directory lock probe, not a manifest-file trial); tmpfs supports the local lock operation but is volatile, so it is not durable storage. `man 1 flock` says “Some file systems (e.g. NFS and CIFS) have a limited implementation of flock(2) and flock may always fail.” `man 2 flock` documents NFS emulation via full-file `fcntl` locks and local-lock mount behavior. No NFS mount was tested (`man 5 nfs` absent; current lane mount is Btrfs per `findmnt -T`, exit 0). On NFS, require server/mount lock support and fail closed on errors; do not claim cross-host exclusion under local-only locking.

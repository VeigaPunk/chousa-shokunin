# C1 parser robustness review

## Findings

1. **HIGH — parse errors can become supported claims (confirmed by source path; end-to-end result is [INFERENCE]).** `verify_claims` accepts a line based only on outer `{…}` shape (`tools/research-gate.sh:1436-1447`), then uses unanchored regex extraction (`:1109-1128`); `jfield` turns reader failure into empty text (`:1119`). There is no JSON parse/encoding validation before the marker-default branch or field checks (`:1448-1525`). Reproducer (same regex shape, not the gate): `timeout 10s bash -c 'line=\'{"id":"X","source":"lib/span.md","span":"alpha beta gamma delta","expect":"supported",}\'; ...'` printed `outer_braces=pass id=X`; the trailing comma makes this invalid JSON. If the source contains the span, the later `supported` path is reachable (`:1527-1581`) and can feed a CLEAN tally (`:1637-1649`). Separately, `read -r` silently removes raw NUL: probe output was `read_len=2 bytes= 41 42` for `A\0B`; Bash also retained invalid UTF-8 (`xff C: len=3 hex= 78 ff 79`). Thus malformed bytes can be normalized before regex matching. C1's counter explicitly excludes invalid JSON (`corpus/evidence/round33/claims.md:80-83`), so it cannot certify this boundary. **Impact:** false supported/clean verification from a record that is not valid JSON. **Smallest fix:** parse raw bytes strictly before any field/default handling; reject invalid UTF-8, raw NUL, malformed JSON, or non-object roots as `CLAIM_RECORD_INVALID`, and `continue` before source resolution. Keep parse status separate from “field absent”; no regex fallback on parser failure.

2. **HIGH — quadratic parsing/unescaping can be a CPU denial of service.** The record loop has no claim-line byte cap (`:1436-1442`; the 8 MiB constant at `:301-305` applies to source files). Trimming repeatedly removes one character (`:1440-1441`); `json_unescape` indexes and appends one character at a time (`:1130-1167`); and span matching builds a regex with a per-character Bash substring/append loop (`:1357-1368`, `:1387-1395`). A 1 MiB span or backslash-heavy field can therefore multiply copying/work quadratically [INFERENCE]. The gate itself documents an analogous repeated-suffix scan as quadratic and replaced it (`:2656-2659`); its `count_nl` comment records an earlier quadratic approach taking >60 s at 8 MiB (`:1170-1174`). **Impact:** attacker-controlled claims can stall `verify-claims`; parser-only optimization will not fix downstream long-span work. **Smallest fix:** use a single linear-time parser/decoder and avoid per-byte Bash slicing/concatenation in any path reached by a parsed span. Enforce a raw physical-record cap (recommend 1 MiB, cap+1 refused) before parsing; enforce a documented depth limit (recommend 128) or an iterative parser; keep parsing one record at a time. The 1 MiB bound is a recommendation, not an existing gate limit. A total-file/claim-count bound is still needed if the whole file is also treated as adversarial, since the current output array grows with record count.

3. **MEDIUM — locale and byte semantics are underspecified for a Bash/awk scanner.** The `json_str`/`json_has_key` regexes and `json_unescape` do not pin `LC_ALL` (`:1109-1128`, `:1130-1167`). Probe: for `${s:i:1}` on `éX`, `LC_ALL=C` reported `len=3`, slices `c3` then `a9`; `LC_ALL=C.utf8` reported `len=2`, slices `c3 a9` then `58`. Existing token scanners explicitly use `LC_ALL=C` (`:1357-1358`, `:1387-1388`), but C locale alone does not validate UTF-8 (the invalid-byte probe above remained intact). CRLF outside a string is valid JSON whitespace; a raw CR inside a string is not, and must not be accepted as ordinary content. **Impact:** locale-dependent scanning/limits and acceptance of byte sequences outside the JSONL encoding contract. **Smallest fix:** preferably decode strict UTF-8 with a JSON library; if a byte scanner is retained, pin `LC_ALL=C`, count bytes, track quoted/escaped state, validate UTF-8 separately, allow CR only as JSON whitespace, and fail closed on unterminated strings/depth overflow.

4. **HIGH — duplicate-key handling must preserve top-level pairs.** Current regex returns the first matching value and `json_has_key` only reports presence (`:1109-1128`), contrary to C1's duplicate-read-key invalidation contract (`claims.md:29-40`). A normal JSON decode into a dict is also unsafe because common decoders overwrite repeated names. Repeated read keys (including thousands) must be rejected before reading any value; nested occurrences must not count. **Smallest fix:** retain object member pairs while parsing; at the root object only, count the seven read keys (`id/source/span/expect/marker/line/sha256`) with a set and invalidate on the second occurrence. Ignore nested same-name members and duplicate unread keys per the frozen contract. Never use regex stripping or brace counting that ignores string escapes.

## Safest implementation shape / resource bound

Use a single strict parser process (e.g. Python 3 stdlib JSON) for `verify-claims`, not a custom Bash/awk JSON grammar; make Python an explicit claims-mode dependency and return setup error 2 if unavailable—never fall back to the old reader. Read binary physical lines with a 1 MiB raw-record ceiling (reject cap+1), strict UTF-8 decode, preflight or otherwise cap nesting at 128, parse exactly one object, preserve root pairs for duplicate detection, and reject nonstandard constants/parse exceptions. Explicitly classify any parser rejection invalid before marker-default dispatch, source lookup, or supported adjudication. Use a safe length-delimited/base64 field protocol (reject decoded NUL in fields passed to Bash); do not send arbitrary decoded strings through command substitution or `eval`. Stream one record at a time. If preserving arbitrary-size spans is required, also replace the existing quadratic Bash unescape/span loops; the record cap alone does not make those loops linear.

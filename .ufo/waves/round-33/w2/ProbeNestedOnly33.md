## Verdict

**HOLDS** for C1 contract item 1 (`corpus/evidence/round33/claims.md`), on the pinned gate `94a7be5a` **and** on
the worktree snapshot `263ffb9d`, across 382 records (66 structured + 16 edge + 300 fuzz):

* a required field supplied only by nesting is `invalid` exactly as if the nested member were absent;
* `"source":{"source":"x"}`-shaped read members are `invalid` (the container is not a string, the nested member is not read);
* several decoy subtrees, depth-5/6/12 nesting and empty containers change **nothing**;
* string content that looks like structure changes nothing;
* the only residual is **out of claim**: lines that are not valid JSON are still accepted when the defect is the
  member grammar *inside* a nested value (claims.md v2: "Not claimed: lines that are not exactly one valid JSON object").

The contract break the ticket asked for was **not found** on either revision. The base gate is broken on the same
inputs in exactly the predicted way (28/45 and 12/20 contract mismatches), which confirms the fixtures do discriminate.

## Method

`verify-claims` was run as the counter runs it — `bash <gate> verify-claims <claims> --root <root>`, with
`CHOUSA_ROOT/RECORD/CLAIMS/STRICT` and `GIT_DIR/GIT_WORK_TREE/GIT_INDEX_FILE` unset — against a temp root holding
`src/a.md` (span `needle span words here` on line 2, sha256 `98248b90…4dae`) and `src/b.md`. Each record's expected
result is derived **independently** by `json.loads(..., object_pairs_hook=…)` on the top-level member list (nested
members are invisible to that reader by construction), plus the documented round-31 `line`/`sha256`/`marker` rules.
Fixtures are hand-written raw JSON so member order and duplicates are controlled; the fuzz corpus is generated by
`json.dumps` so every line is valid JSON.

## Result 4 — "changes nothing", measured as an equivalence

I rebuilt each claims file with every non-read top-level member deleted (`fixtures/claims-stripped.jsonl`,
`claims2-stripped.jsonl`) and compared CLAIM lines and findings:

* `claims.jsonl`: **45/45 CLAIM lines byte-identical**, 27/27 findings identical (line numbers normalised);
* `claims2.jsonl`: **20/21** — the one difference is `H11`, whose key is spelled `"i\u0064"`; stripping re-emits the
  decoded key, so the transform (not the gate) changed the record. `H11` is the explicitly *not-claimed* escape case;
  observed `invalid` (`missing id`), consistent with the documented limit.

So on the landed gate a record with decoy/nested-only members produces exactly the output of the same record with
those members deleted — the contract's "a nested member … changes nothing", empirically.

## Out-of-claim residual: the fail-closed boundary is partial

`fixtures/malformed.jsonl` holds 14 lines that Python's `json.loads` rejects. Accepted as **valid claims**
(`observed=supported`):

| line | `94a7be5a` | `263ffb9d` |
|---|---|---|
| `{"meta":{"a":1,},"id":"M1","source":"src/a.md","span":…,"expect":"supported"}` (trailing comma in a nested object) | accepted | accepted |
| `{"meta":{"a":1"b":2},…}` (missing comma between nested members) | accepted | accepted |
| `{"meta":{"a" 1},…}` (missing colon in a nested object) | accepted | accepted |
| `{"meta":{a:1},…}` / `{"meta":{"a":bare},…}` (bare token) | accepted | **rejected** |
| `{"meta":{"a":1} x,…}` (garbage after a nested value) | rejected | rejected |
| top-level trailing comma / missing comma / garbage / unquoted key / array / two objects / unbalanced / mismatch | rejected | rejected |

`claims.md` v2 puts "lines that are not exactly one valid JSON object" outside C1, and `263ffb9d`'s comment now states
the same limit ("Not checked (as at base): raw control bytes inside strings, and the member/element grammar inside
nested values beyond bracket balance and bare tokens"). So this is a **documented, out-of-claim** gap, not a C1 break:
`verify-claims` still reports `observed=supported` for a line a JSON parser rejects. It is the only place where the
gate's "one well-formed JSON object" promise and its behaviour differ on my inputs.

## Limits

* The fuzz expectations and the invalid *reasons* encode the documented round-31 rules (missing/empty span, line/sha
  validity), so a systematic misreading shared by my oracle and the gate would be invisible; the C1-specific part
  (nested members are not read) does not depend on those rules — it is measured by base-vs-landed and by Result 4.
* Keys spelled with JSON escapes are explicitly not claimed; only `H11` probes them.
* Raw control bytes inside strings, other `verify-*` modes, and very long lines (performance) were not probed.
* The worktree is a moving target: my worktree numbers are for `263ffb9d` only; the file was already `165acd5f` when I
  finished. Any later revision needs a fresh run of `fixtures/claims*.jsonl` and `fixtures/fuzz.jsonl`.
* No subagent was used; no background job was started by me (one oracle run was auto-backgrounded by the harness and
  its result is included).

## Findings
1. **HIGH — the frozen code condition is not implemented.** claims.md:49-50 freezes `Code condition: matched == 7`; `c1-count.py:233-240` computes `total = len(rows)` and `holds = matched == total`, and `:255` hard-codes `"predicate": "ENV_PIN_CAPTURE_MATCH=7/7"` regardless of `total`. Evidence 4: a six-scenario counter prints `6/6`, exits 0, and emits a receipt that literally asserts `predicate: 7/7` with `predicate_holds: true`, which `verify-receipts.py:114-117` accepts (it checks only `matched == recount`, `total == len(scenarios)`, and `predicate_holds == (matched == len)`; `predicate` is not in `REQUIRED` and is never compared). The P1 acceptance test can therefore be satisfied by a shortened scenario table; `predicate_holds` alone is not the frozen condition. Required fix: hard-require `total == 7` (and `SCENARIO_ORDER`/expectation-id identity) for `holds`, derive the printed/receipt predicate from `matched`/`total`, and have the verifier reject `total != 7` and any `predicate` that contradicts the arithmetic. The global `matched == total` also makes the kill rule's "below 7/7" undefined for a `6/6` run (see finding 2).
2. **HIGH — the kill rule is triggerable by the measurement environment, not the gate.** claims.md:52-54. Evidence 5: with the landed gate bytes unchanged (`gate_sha256` matches), the committed counter and expectations, and a fresh seed, an ambient `PATH` wrapper yields `ENV_PIN_CAPTURE_MATCH=2/7` and a receipt that `verify-receipts.py` accepts. By the literal rule ("Any run against the landed gate below 7/7 kills C1; a run whose receipt `gate_sha256` differs … is not the claim's measurement") C1 dies, although only the harness `PATH` changed; `c1-count.py:base_env()` scrubs `BASH_FUNC_*`, `CHOUSA_*`, `RESEARCH_GATE_*` but not `PATH`, `BASH_ENV`, `LD_PRELOAD`, `TMPDIR` or `SHELLOPTS`. The identity guard is also one-sided: it binds gate bytes but not counter bytes, expectation bytes or the run environment, and P1's "the same counter" is never operationalised. Concrete canonical killing run for the record: `C1_TMP=/tmp/<new> python3 corpus/evidence/round38/c1-count.py --gate tools/research-gate.sh --seed <fresh> --receipt /tmp/<kill>.json`; it printed 7/7 at seed 38201, so C1 survives this wave. Fix: a run kills C1 only when gate, counter and expectations bytes all match the committed artifacts **and** the environment is scrubbed/pinned (at minimum `PATH`, `BASH_ENV`, `LD_PRELOAD`, `TEMPDIR`/`TMPDIR`, `SHELLOPTS`), or the rule must say the counter owns its environment.
3. **MEDIUM — the named bash limit identifies the wrong call site and omits the live vector.** claims.md:130-132 says a caller-exported function `bash` "can still shadow the capture's bare `bash` call" and calls the "grandchild `bash` lookup" the next witness. Evidence 7: the capture's `bash` is an **argument to the pinned `env`** (`research-gate.sh:4000-4004`), so the exported function is not consulted for it (0 hits); its 5 hits are the `verify_all_section` shell-outs (`research-gate.sh:3642`), i.e. the grandchild class only. The vector that does substitute the capture child is `PATH` resolution inside `/usr/bin/env`: evidence 6 reproduces `GATE_GREP:` embedding plus phantom `-GATE_GREP` drift on the landed gate, and evidence 8 shows a suppressing `bash` function lets `--pin` exit 0 while pinning a `severity=crit` `VERIFY_ALL_SECTION_UNAVAILABLE` baseline (baseline poisoning, not merely "shadowing"). The limit must state: C1 pins the launch `env` only; the launched `bash` remains `PATH`-selected (the real next witness), and exported functions named `bash` reach the five section subshells and can poison a successfully pinned baseline.
4. **LOW — "two fresh seeds" is not independent replication for C1.** P1 (claims.md:48-49) requires two fresh seeds, but `--seed` is written only into the receipt (`c1-count.py:194,218,247`) and never namespaces fixtures or work dirs; the two committed receipts are byte-identical modulo `seed`/`receipt_sha256` (evidence 11). C2's limits disclose the analogous inert-seed fact; C1's do not. Either name it ("the seed is a receipt label; the run is deterministic") or seed the `mkdtemp` and fixture paths.
5. **LOW — "verified GNU coreutils" is not recorded in the artifact.** claims.md:31-32 asserts the default pin is "verified GNU coreutils"; the check is a first-line `--version` substring (`research-gate.sh:480-493`) and the receipt binds no `ENV_BIN` path, version or source, so a committed receipt cannot show which `env` adjudicated the run. The self-report limit (claims.md:145-146) is honest about the check's reach, but the claim sentence and the limit are in tension. Adding `env_bin`, `env_version`, `env_source` to the receipt would close the calibration gap.
6. **LOW — "before any mode runs" is code-evident but unmeasured.** claims.md:32-34 generalises the `ENV_PROVENANCE` refusal to every mode; the seven cells exercise `--pin` only. `env_pin_init` at `research-gate.sh:8537` precedes the `case "$MODE"` dispatch, so the generalisation is supportable, but no cell demonstrates a non-pin mode refusing.

**Overreach answer (QUALITY 52/54 class):** the C1 claim sentence itself is correctly mechanism-scoped — "a caller-exported shell function named `env` … cannot interpose on the capture call" is a universal over function bodies, but it is grounded in the absolute-path invocation and I measured 0 invocations of an exported `env` function on the pin path (evidence 10), so it is not an overreach beyond the seven cells. The overreach-class defects live in the limits (finding 3) and in the two-seed framing (finding 4), not in the claim sentence. C1's predicate is **not** falsified by the PATH vector: that channel is outside the claim's stated scope, but it is inside the operability threat model the limits purport to name.

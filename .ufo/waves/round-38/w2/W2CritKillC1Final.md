## Findings
1. **named-limit (Erratum 6 wording drift)** — `claims.md` Erratum 6(a) says “a parent-exported `date` function still embeds a `GATE_GREP:` line and a phantom `-GATE_GREP` drift on the landed gate”. The `date` function alone cannot do that: `CHOUSA_GREP_PIN_ECHO=1` must be live in the capture environment (measured: parent env with exported `date`, no echo variable, baseline contains zero `GATE_GREP:` lines). The embedding happens only when `BASH_FUNC_date%%` is combined with `CHOUSA_GREP_PIN_ECHO=1`; the preload witness above proves that combination is reachable on final bytes (`echo_lines=1`, phantom `-GATE_GREP`, clean drift rc 1). The live mechanism is sound, but the erratum wording omits the required variable condition. Smallest safe correction: amend the erratum sentence to “with `CHOUSA_GREP_PIN_ECHO=1` also exported/ambient”.
2. **out-of-scope for C1 (sibling-name witnesses beyond `date`)** — exported `grep` and `sha256sum` functions import but never receive the gate's pinned calls: wrapper definitions call `$GREP_BIN`/`sha256_pin_bin` absolute paths (`tools/research-gate.sh:356-362`, `:432-454`), and the sibling logs are empty. Only `date` remains genuinely sibling-open because startup timestamping uses bare `date` (`:327-330`). This strengthens, not weakens, C1's exact “capture `env` invocation” scope.

4. **named-limit confirmed (`RESEARCH_GATE_ENV`)** — the override is honoured, pre-flight (`--version`) and capture (`-u … bash …`) both route through the wrapper, and the run remains clean. The claims' wording “RESEARCH_GATE_ENV override, absolute + GNU-reporting, refused exit 2 with ENV_PROVENANCE before any mode runs” matches observed capture use; no discrepancy found.

## Findings
1. **INFO — Network:** no `socket()` or `connect()` call was observed in any traced command. No egress exploit path was observed; impact is limited to this syscall sample. Smallest remediation: none indicated by this surface.
2. **INFO — C2 run invalidated by shared-tree mutation:** C2 started with the frozen `37e2…` gate hash, detected changed bytes, exited 2, and published no receipt. Its trace made no write-capable `openat` to the gate; the post-run tree showed the gate dirty and hash `0447…`. [INFERENCE] A concurrent/out-of-band writer is consistent with this evidence; the writer was not identified. Impact: C2 result is correctly fail-closed, but no stable-gate receipt was produced. Smallest remediation: freeze the gate/worktree for the run and repeat only under a stable snapshot.
3. **LOW, conditional — Python user-site startup surface:** the Python interpreter opened `/home/vgpnk/.local/lib/python3.14/site-packages` (directory only; no file below it was opened in these traces). [INFERENCE] If an attacker-controlled `.pth`/package is present, Python startup can affect counter output/receipt integrity before counter code runs. Smallest remediation if that directory is outside the trust boundary: launch every parent/child Python invocation in isolated mode (`-I`) or otherwise disable user-site and scrub Python import-path variables.

## Limits
- C1 and the standalone verifier bind/verify the original `37e2…` gate bytes. C2's guard correctly rejected the mid-run change; no C2 receipt was available to verify. No edit or counter rerun was performed after observing the dirty gate.
- The trace is syscall evidence for these runs only; it does not establish behavior under other locales, Python installations, or caller environments.

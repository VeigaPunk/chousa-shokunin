## C. Why the guard is load-bearing: the census accepts the indented row as a registry row

`/home/vgpnk/Projects/shokunin/scripts/sources-census.sh` row_pass() matches rows with 0-3
leading ASCII spaces (line 615: `if (line !~ /^ {0,3}\|/) next`; line 616: `sub(/^ {0,3}/,"",line)`),
so a two-space-indented row IS a registry row to the census — the column-zero-only extractor
would miss a duplicate the census still reports as E03.

Fixture: a two-row registry (S001, S002) with a `corpus/knowledge/x.md` so used-by resolves.

    $ bash /home/vgpnk/Projects/shokunin/scripts/sources-census.sh validate --file "$C3/corpus/SOURCES.md"
    file    ok      .../guard/census3/corpus/SOURCES.md
    exit=0   (no indented row: census-valid)

    $ bash /home/vgpnk/Projects/shokunin/scripts/sources-census.sh validate --file "$C3/corpus/SOURCES-with-indented.md"
    file    E03     S002 duplicate id
    exit=1

Indent tolerance boundary (same fixture, one indented duplicate at indent 1..4):

    indent=1 -> 1 E03 duplicate-id finding(s)
    indent=2 -> 1 E03 duplicate-id finding(s)
    indent=3 -> 1 E03 duplicate-id finding(s)
    indent=4 -> 0 E03 duplicate-id finding(s)

The census sees the indented duplicate at 1-3 spaces and not at 4: the 0-3-space extractor
matches the census's own tolerance exactly.

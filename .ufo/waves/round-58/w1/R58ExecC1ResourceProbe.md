## Method
Peak RSS = child's kernel hwm `VmHWM:` from `/proc/<pid>/status`, polled every 2 ms by the parent
(execve resets the mm hwm, so no fork-inherited noise); wall clock `time.monotonic()` around
`communicate()`; every child ran with `cwd` and `TMPDIR` inside scratch. Fixtures were generated by
**importing the frozen counter read-only** (`importlib` on `corpus/evidence/round58/c1-count.py`), so
the bytes are the counter's own (`synth_text`, `synth_quotes`, `write_quotes`, `key`, `QUOTES_CAP`).
    python3 probe2.py <case> tools/build-spans.py        final/<case>-base    90
    python3 probe2.py <case> tools/build-spans-guarded.py final/<case>-guarded 90
    python3 …/corpus/evidence/round58/c1-count.py --builder tools/build-spans.py \
        --controls …/controls --work <scratch>/ctr/base-ctl
`probe2.py` = harness; `tools/build-spans-guarded.py` = scratch copy of base + this report's guard
(never a lane file).

## F1 — yes, the base reads an oversized body (unbounded)
`tools/build-spans.py:80` `b = raw.read_bytes()` runs **before** capture-text is consulted (line 82);
`:86` `b = txt.read_bytes()` is the `.txt`-sidecar branch (no cap exists there — capture-text is never
involved); `:99` `path.read_text().splitlines()` reads the whole quote table. The only size bound in the
toolchain is `capture-text.py`'s `MAX_PART = 256 MiB`, a *render* cap applied after the builder already
read the body, and it does not cover the `.txt` branch.

Sparse OLE-headed `.raw` fixtures (the counter's FAT_RAW shape), 90 s bound:

| body | base peak RSS | base elapsed | base refusal text |
|---|---|---|---|
| 80 MiB (counter FAT_RAW) | **181.5 MiB** | 0.120 s | `capture-text refused …: ole-malformed: sector shift 0` |
| 256 MiB | **533.3 MiB** | 0.312 s | `ole-malformed: …` |
| 512 MiB | **788.2 MiB** | 0.423 s | `OLE file larger than 268435456 bytes` |

At 512 MiB the peak exceeds the file size: the builder's `read_bytes()` (512 MiB) is live simultaneously
with capture-text's own `f.read(MAX_PART + 1)` copy (~256 MiB). Per-stage attribution (`stage.py`):
    stage=start      hwm_kb=16312
    stage=head8      hwm_kb=16464
    stage=read_bytes len=83886080 hwm_kb=98452      <- builder's own unbounded read
    stage=sha256     hwm_kb=98516
    stage=capture_text refused=ole-malformed: sector shift 0, mini shift 0
    stage=end        hwm_kb=182816  rss_kb=101744   <- second copy inside capture-text
The `.txt` sidecar branch is equally unbounded (no OLE/zip header, so `read_bytes()` is the only read):
80 MiB sidecar → 180.7 MiB peak; 256 MiB sidecar → 532.3 MiB peak. Nothing times out — the cost is
memory, so a timeout-only bound would not catch it.

## F2 — MANY_QUOTES: unbounded rows, unbounded write amplification
The frozen fixture is `QUOTES_CAP + 1 = 100001` rows, all on the same `.txt` capture, quote occurring
exactly once. The base **accepts** it (rc=0) and materialises the whole set:
    CASE=many RC=0 TIMEOUT=False ELAPSED_S=2.047 PEAK_RSS_KB=151512 PEAK_RSS_MIB=148.0
    out dir: 100002 files, 36,389,311 logical bytes, 413 MB on disk (spans.tsv alone 18,389,131 B)
148.0 MiB peak, 2.047 s (inside the counter's 90 s leg timeout), but 413 MB written and 100 k inodes.
`read_text().splitlines()` (line 99) is the read behind the 148 MiB.

## F3 — the smallest measurable guard
Two checks, each *before* any body byte is read and before any write. Caps reused verbatim from the
frozen counter (`c1-count.py:49-50`), not re-chosen.

**G1 — capture body size.** One `stat()` per capture file vs `SIZE_CAP = 64 MiB`, reason contains `SIZE`:
    CASE=fatraw RC=1 TIMEOUT=False ELAPSED_S=0.032 PEAK_RSS_KB=20336 PEAK_RSS_MIB=19.9
    build-spans: refused S551: SIZE cap: capture f96cbd6d82dbae8a8e2c6223.raw is 83886080 bytes (limit 67108864)
Peak 181.5 → 19.9 MiB (≈9×), elapsed 0.120 → 0.032 s, and the refusal now precedes the body read, so
peak is flat (19.8 / 19.9 MiB) at 256 MiB and 512 MiB bodies too.

**G2 — quote-table row count.** Row counter in `read_quotes`, reason contains `ROWS`, before any write.
Two variants measured:
* accumulate-then-check (count while parsing): `CASE=many RC=2 … ELAPSED_S=0.241 PEAK_RSS_MIB=54.1`
* two-pass count-first (count lines, refuse, then parse): `CASE=many RC=2 … ELAPSED_S=0.032 PEAK_RSS_MIB=19.8`
Two-pass is the smaller guard in memory (19.8 vs 54.1 MiB) at the cost of a second read of a table that
is refused anyway; it is the variant I would propose. Both write nothing (`out-many` empty), both well
inside the leg timeout.

## Risks / limits
* Numbers are from this host (32 cores, 31 GB RAM, /fast, Python 3.14.8), one case per process.
  Absolute MiB is host-dependent; the transferable claim is the ratio and that peak is now flat in body
  size instead of scaling with it.
* The row sweep at 10 k / 100 k rows over a 400 k-line capture gave the base 33.4 s / 369.1 s — a
  per-row O(capture) cost that dwarfs the frozen fixture's 2 s. The 300 k-row point was aborted at my
  900 s harness bound and its outputs deleted; that quadratic is an observation about line 145, not a
  frozen-leg claim. G1/G2 were measured on a scratch copy only; no patch is applied to any lane file.
* HELDOUT_OK exercised the real S101 capture and passed for both builders, so the 64 MiB cap excludes no
capture the lane currently holds (S101 capture = 129,024 bytes).

VERDICT: The existing (base) `tools/build-spans.py` does read an oversized body — `raw.read_bytes()`/`txt.read_bytes()` (lines 80/86) pull the whole capture into the builder's memory before any size check (measured 181.5 MiB peak for the frozen 80 MiB FAT_RAW fixture, 533.3 MiB at 256 MiB, 788.2 MiB at 512 MiB) and it accepts the frozen 100,001-row MANY_QUOTES table, writing 100,002 files / 413 MB at 148.0 MiB peak; the smallest measurable guard surviving both is a pre-read `stat()` size check against the counter's own 64 MiB `SIZE_CAP` plus a pre-write row count against its 100,000 `QUOTES_CAP` (measured FAT_RAW 181.5 → 19.9 MiB, MANY_QUOTES 148.0 → 19.8 MiB with zero writes, normal S101 output byte-identical), and running the unmodified frozen counter shows that guard flips exactly FAT_RAW and MANY_QUOTES to `pass(refused)` with all safe legs and HELDOUT_OK still green — the resource hazard **survives** as real, and the guard **survives** as the minimal fix for the two resource legs; the other five refusal legs remain open and out of this seat's scope.

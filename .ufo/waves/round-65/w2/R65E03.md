## Mechanism (grounding)

- `c1-count.py:20` — a case passes iff the tool's exit code equals the case's
  expected rc, and (for rc=0 cases) stdout is exactly `RECEIPT_PIN=PASS`, and
  (for rc=1 cases) stdout starts with `RECEIPT_PIN=FAIL `. The 20-case matrix
  mixes 3 well-formed receipts (expected accept) with 17 malformed receipts
  (expected reject) (`c1-count.py:16`, case list).
- `controls/always-pass.py:1-2` — prints `RECEIPT_PIN=PASS`, exits 0 for every
  input regardless of receipt content.
- `controls/always-fail.py:1-2` — prints `RECEIPT_PIN=FAIL stub`, exits 1 for
  every input regardless of receipt content.

## Verdict

**No falsification.** Both do-nothing controls reproduce the committed receipt
byte-for-byte in aggregate (`CASES=3/20 C1=FAIL` exit 1 and
`CASES=17/20 C1=FAIL` exit 1).

**Can a do-nothing or always-passing tool reach the 20/20 target? No.**
An always-pass tool caps at 3/20: it satisfies the 3 well-formed accept cases
but cannot reject any of the 17 malformed receipts (`c1-count.py:20` requires
exit 1 plus a `RECEIPT_PIN=FAIL ` prefix for those). An always-fail tool caps
at 17/20 by symmetric argument (it rejects the 3 well-formed cases the counter
requires to be accepted). The expectation matrix forces genuine per-receipt
validation of header consistency (revision line, exit line, SHA256 digest,
path safety); a content-blind tool of either polarity structurally cannot
satisfy both halves of the matrix. The 20/20 target is therefore not reachable
by do-nothing or always-passing stubs — it requires a real validator such as
`tools/receipt-pin.py`.

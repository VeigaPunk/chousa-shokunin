## Answers

1. **Yes — a consistent receipt with a reported failing child exit validates.**
   `EXIT=7` is accepted: `tools/receipt-pin.py:42` only checks the header
   matches `EXIT=(?:0|[1-9][0-9]{0,2})` and `int(...) <= 255`. Exit code is
   treated as an opaque reported datum, with no semantic weight on pass/fail
   of the child. So PASS does not imply the recorded command succeeded.

2. **Yes — a fabricated body still validates.** The body is checked only for
   nonemptiness (`tools/receipt-pin.py:53`). A header-consistent receipt whose
   body is invented wholesale (no command ever ran) yields `RECEIPT_PIN=PASS`,
   exit 0.

Both behaviors match the tool's own disclaimer: PASS proves only
self-consistency with the pinned blob, "not that a command truly ran or that
the body is truthful" (`tools/receipt-pin.py:10-12`). Falsification attempt:
**no defect found** — the tool behaves exactly as specified and disclaimed;
the header-consistency capability (C1 operability) and the sourced-interpretation
claim (C2 depth, where the body is the interpretation) are the honest limits
the receipts and lessons already state. This is a positive-control
confirmation, not a vulnerability: any lane prose that reads a round-65 PASS
as execution evidence would overclaim, but the docstring and (per lane
context) `corpus/lessons/round-65.md` disclaim exactly this.

## 2. Direct answers to the two questions asked

**Does every mutation drop the score below 10/10? NO.** Four probes of the twelve scored
`ENTRY_CHECKS=10/10 C2=PASS` with `EXIT=0`: M2a, M2b, M2c (the `source:`-line citation removal
that the item names) and M6 (source header citing ids that do not exist). M5b, the content-free
forgery, also scored 10/10. Only the whole-file token removals (M2d/M2e/M2f), the header-line
removals (M1, M3) and the README name removal (M4) were killed.

**Can the counter be satisfied without the real entry? YES — content-wise.** M5b: a 116-byte
stub at `corpus/knowledge/receipt-identity-r65.md` containing nothing but the ten required
tokens yields `ENTRY_CHECKS=10/10 C2=PASS`, `EXIT=0`, with no claim, no quote, no source
citation and no limit prose present. (M5, the same stub missing `## Limits`, was correctly
scored 9/10 — the check itself works; it is the *content* it cannot see.) The counter's own
docstring (`corpus/evidence/round65/c2-count.py:2`) states it is a "structural sourced-entry
counter; does not establish entailment", so M5b/M6 are consistent with the declared contract —
they are coverage findings about what the 10/10 score does and does not attest, not evidence
that the contract was broken.

## 3. Findings, each with what it attacks

**F1 (coverage finding, survives) — the `source:` header's citations are unguarded.**
`corpus/knowledge/receipt-identity-r65.md:1` is the entry's provenance header
(`source: S154 — installed git-cat-file(1), Git 2.56.0, OUTPUT; S155 — …; S156 — …`).
Check 4 (`c2-count.py:8`) is `all(x in text for x in ['S154','S155','S156'])` — a whole-file
token test. The same ids also occur in the claim bodies at `receipt-identity-r65.md:9`
(`1. S154's installed manual …`), `:10` (`2. S155's hashlib …`) and `:11` (`3. S156 begins …`),
so removing an id from the `source:` header leaves the token present and the score at 10/10
(M2a/M2b/M2c). Only removing the token from the entire file trips check 4 (M2d/M2e/M2f → 9/10).
Consequence: an entry whose source header has been stripped of its citations still scores
"depth = sourced interpretation entry" at 10/10. The C2 depth claim is enforced at
whole-file token granularity, not at header granularity.

**F2 (coverage finding, survives) — cited ids are never reconciled with `corpus/SOURCES.md`.**
Check 5 (`c2-count.py:8`) tests `all(('| '+x+' |') in s for x in ['S154','S155','S156'])`
against `corpus/SOURCES.md` — rows `S154`/`S155`/`S156` exist at `corpus/SOURCES.md:164-166`
(`S157` at `:167` is the rejected source). Check 5 is independent of what the *entry* cites.
M6 rewrites the entry's header to `S1549 / S1559 / S1569` — ids that exist nowhere in
`corpus/SOURCES.md` — and the counter still reports `ENTRY_CHECKS=10/10 C2=PASS`, exit 0. A
`sourced` entry can therefore cite a non-existent source and still score full depth.

**F3 (coverage finding, survives) — the 10/10 score is a shape score, not an evidence score.**
M5b: a 116-byte token stub satisfies all ten checks and the counter exits 0 with the real
entry's substance absent. Any future claim of the form "C2 depth = 10/10" should be read as
"the entry has the required structural shape", never as "the entry carries sourced
interpretation". If the verdict text needs the stronger reading, the counter cannot support
it; a separate content check (e.g. claim-body/quote non-emptiness, or a per-id citation check
against `corpus/SOURCES.md`) would be required — that is L1's call, not this seat's.

**F4 (killed — the counter is not vacuous at the levels it does police).** M1 (`verified-at:`
header line), M3 (`## Limits` heading, `receipt-identity-r65.md:14`) and M4 (entry name removed
from `corpus/README.md:1342`) each drop the score to 9/10 with exit 1, and the discriminator
removals M2d/M2e/M2f do the same. M5 (forgery missing `## Limits`) was also caught at 9/10.
The counter does hold the line on: header presence, the `verified-at:`/`recheck:` header lines,
the two section headings, the two required words, the README cross-reference, and total absence
of a cited id. So the counter is a real (if shallow) gate — it is not satisfiable by an empty
or malformed file.

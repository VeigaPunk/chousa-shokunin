# R65N01 — Sibling-lane overlap scan: receipt / attestation / execution-proof gates

Seat: R65N01 (chousa round-65, wave w2, falsify lane). Read-only scan of the 20 sibling
`*-shokunin` repos under `/home/vgpnk/Projects/shokunin` (chousa itself excluded).
No sibling files were modified; no network; no git mutations.

## Method (commands actually run)

1. `ls -d /home/vgpnk/Projects/shokunin/*-shokunin` — 21 lane repos; 20 siblings.
2. Per-sibling presence check: `[ -f SKILL.md ]`, `[ -d corpus ]`, `[ -d tools ]`.
   `audio-shokunin` and `game-dev-2d-shokunin` have **no SKILL.md** (corpus only).
3. Case-insensitive grep of every sibling's SKILL.md + corpus/ for
   `receipt|attestat|sha256|sha-256|digest|cat-file|exit[- ]?code` (`.jj` op-store
   binary noise excluded by re-searching text paths directly).
4. Header reads of every hit that turned out to be a tool/validator (see below).

## Bottom line

- **No sibling owns chousa's exact capability**: a *validator-only* checker of a frozen
  receipt **header** (`REVISION=`/`EXIT=`/`SHA256=<digest> <repo-relative path>`) against
  `git cat-file blob <rev>:<path>` bytes. The two nearest owners are **souji**
  (`tools/souji-receipt-run.py`, blob-bound receipts) and **tameshi**
  (`tools/receipt-revision-gate.py`, receipt-to-revision binding). Both are the same
  capability family (receipt-header/git-object consistency) but differ in scope and
  role. **`tools/receipt-pin.py` is complementary to both — it does not duplicate or
  conflict.**
- **One sibling claims a general-ish attestation capability**: **kumitate**
  (`scripts/receipt-attest.mjs` / `receipt-evidence.mjs`, knowledge entry
  `corpus/knowledge/invocation-attestation.md`). Its declared ceiling is verbatim the
  same as chousa's (`receipt-identity-r65.md` "Receipt identity is not execution
  authenticity"), so chousa's narrow scope reads as **aligned/subordinate, not
  competing**.
- All other receipt/hash usage in siblings is either (a) receipt *production* as run
  records with producer-digest binding for their own gates (mado, game-dev-2d, tabi,
  kengaku), (b) domain-specific receipt schema validation (kama), or (c) content
  pinning of fixtures/knowledge (lore, kaidoku, game-dev-3d, kasegi). None validates a
  receipt header against git blob bytes the way round-65 does.

## 1. Direct receipt-consistency / execution-evidence gates (nearest neighbors)

### 1a. souji-shokunin — blob-bound receipts (CLOSEST match)

- `souji-shokunin/tools/souji-receipt-run.py:2` — docstring: "souji-receipt-run.py —
  blob-bound receipts (round 23, C2). A counter run is only evidence if the bytes that
  produced it are pinned."
- `souji-shokunin/tools/souji-receipt-run.py:97` —
  `HEADER_ORDER = ("receipt", "rev", "tool", "tool_sha256", "cmd", "rc", "utc")` — a
  frozen v1 receipt header, then stdout/stderr fences.
- `souji-shokunin/tools/souji-receipt-run.py:39` — "`verify` exits 2 with one of:
  RECEIPT-MALFORMED, RECEIPT-TOOL-DIGEST-MISMATCH, …" — verify re-reads the tool bytes
  from git and refuses a receipt whose recorded digest is not the committed blob at
  the named revision (`cmd_verify` at `:334`, refusal at `:352`).
- `souji-shokunin/corpus/QUALITY.md:129` — criterion Q55: "A count quoted in a lane
  record must name a receipt that binds the revision and the sha256 of the bytes that
  produced it … `python3 -B tools/souji-receipt-run.py verify --root . <receipt>`
  exits 0 for every receipt a record cites; a receipt whose recorded digest is not the
  committed blob at its `rev=` must be refused (`RECEIPT-TOOL-DIGEST-MISMATCH`)."

**Relationship to chousa `tools/receipt-pin.py`: COMPLEMENTARY (near-neighbor).**
Same technique (receipt header vs committed git blob, read-only git, fail-closed exit
codes) and same honesty posture, but three structural differences:
1. **Subject of the digest** — souji binds the *tool* blob that ran (`tool_sha256` at
   `rev`), plus `cmd=`/`rc=`; chousa binds an *arbitrary repo-relative measured file*
   blob (`SHA256=<digest> <path>`) with no cmd binding.
2. **Role** — souji is producer+verifier (`run` executes the command in a private
   `--no-local` clone and writes the receipt; `verify` checks it); chousa is
   validator-only against an externally authored receipt.
3. **Semantics of `rc`/`EXIT`** — souji's `rc=` records the runner's own child exit;
   chousa's `EXIT=` is an asserted reported exit whose consistency (not authenticity)
   is the entire claim (see `corpus/knowledge/receipt-identity-r65.md:44` — "`EXIT=1`
   can be a consistent report of a failed command").
No shared format, no shared code, no shared receipt subject → no duplication; no
constraint that one lane's receipts satisfy the other → no conflict.

- Also `tameshi-shokunin/tools/receipt-window.py:1-10` (receipt must name instrument
  sha256 + measurement interval within the edit window) and
  `tameshi-shokunin/tools/receipt-measure.py:1-5` (runner binds instrument identity).

**Relationship: COMPLEMENTARY.** tameshi checks that a receipt's *named revision* is
the revision under test (rev-token resolution, ancestor/content-drift checks over its
own receipts). chousa checks that a receipt's *digest header equals the blob bytes at
a caller-pinned revision*. A tameshi-style gate would catch a receipt naming the wrong
rev; a chousa-style gate catches a digest that doesn't match the named rev's blob.
They attack different seams and could be composed; neither subsumes the other.

## 2. The one general attestation claim (competition check)

### kumitate-shokunin — receipt-attest / invocation attestation

- `kumitate-shokunin/SKILL.md:624` — registry gate row: `scripts/receipt-attest.mjs
  run|verify` → `RECEIPT: VALID|REPLAY|TAMPERED`, contract `kumitate-receipt-attest-v3`
  (sidecar-over-whole-file + inner-digest binding, monotonic spans, nonces, ledger
  freshness); hermetic suite at `SKILL.md:732`.
- `kumitate-shokunin/SKILL.md:620` — `scripts/receipt-evidence.mjs` (round 58): a
  receipt set is evidence only if every receipt verifies under the extraction's own
  receipt-attest and reproduces its recorded argv in the `git archive` extraction of
  the judged rev.
- `kumitate-shokunin/corpus/knowledge/invocation-attestation.md:1-6` — admitted round
  51 (C2): "Invocation attestation — why receipts are built the way they are"; scope
  "what a receipt must bind so a copied body with a rewritten display prelude is
  machine-detectable, and which ceiling stays open."
- `kumitate-shokunin/corpus/knowledge/invocation-attestation.md:37` — the ceiling:
  "attestation proves record integrity and ledger nonce freshness, NOT temporal truth.
  Q39's ceiling stands verbatim: receipts are author-attested invocation records, not
  cryptographic temporal proof."

**Reading:** this is the sibling a casual reader could see as chousa competing with —
both produce/verify "did this run really produce these bytes" machinery. It is not a
competition, for three reasons: (1) kumitate's instrument attests *invocations of its
own gate counters* (monotonic span, nonce, ledger), a stronger and different claim than
chousa's header/blob consistency; (2) both lanes declare the identical ceiling —
kumitate "NOT temporal truth" vs chousa `receipt-identity-r65.md` "Limits: This format
does not prove execution authenticity… No command/body binding, signature, trusted
timestamp or process attestation"; (3) chousa's tool is scoped to one frozen round-65
receipt shape and explicitly disclaims execution authenticity, so it sits *below*
kumitate's attestation plane rather than overlapping it. **Verdict: complementary,
ceiling-aligned; chousa should cite kumitate's entry as the fleet's stronger instrument
if the L1 wants to ward off the competition reading.**

## 5. Risks / notes for L1 integration

1. **Duplication risk: LOW.** The round-65 format (REVISION/EXIT/SHA256-path header,
   validator-only, measured-file blob) is not owned by any sibling. The nearest
   neighbors (souji, tameshi) differ in receipt subject and role. If a future wave
   wants to *produce* round-65 receipts, souji's runner pattern is the prior art to
   cite, not to copy.
2. **Competition reading: only from kumitate**, and defused by its own ceiling
   statement (item 2 above). If QUALITY.md criterion 130 is challenged as "kumitate
   already owns attestation", the honest answer is that receipt-pin.py disclaims
   attestation by design and both lanes state the same limit.
3. **No cross-lane write or format coupling exists**; nothing in the siblings
   constrains chousa's frozen counters or the S154–S157 source rows.
4. Tooling installs: none (only read/grep). No packages installed, no pacman, no
   network.

## Claim

`QUALITY.md` criterion 6 asks every admitted `knowledge/` entry for three
header facts: where it came from (`source:`), when and what was checked
(`verified-at:`), and when it is due again (`recheck:`). Until round 25 no mode
read them, so an entry missing one was invisible. `verify-metadata PATH`
screens one entry or a directory of entries and names each missing or malformed
key; on the lane's 28 entries at the round-25 base it reports
`METADATA_COMPLETE=25/28`, exit 1, naming `archives-verified-r9.md`,
`audit-r11.md` and `gate-baseline-r8.md` (`META_RECHECK_ABSENT` each) — the
three legacy headers `lessons/round-24.md` M-13 listed. Observation:
`corpus/evidence/round25-measure-after.log`.

Why these three keys (inference from S029 and S033, each within its row's
scope): the Cochrane Handbook calls for periodic currency assessment
(S029, "All Cochrane reviews should be assessed periodically to determine
whether an update is needed"), which a record can only support if it says when
its next check is due; PROV-O records derivation (`prov:wasDerivedFrom`) and
entity-lifetime times (`prov:generatedAtTime` / `prov:invalidatedAtTime`) as separate
facts (S033), which is the split between `source:` and `verified-at:`. Neither
source prescribes this header; the header is the lane's own convention.

## The move

- Header region: lines before the first `## ` heading outside a fenced block;
  trailing `\r` stripped. Key lines `source:`, `verified-at:`, `recheck:` at
  column 0, outside fences; a value runs to a blank line, another key line or
  the header end. Only those three keys end a value (a continuation line such
  as `note: …` stays inside it — selftest case 153).
- Findings (surface `metadata`): `META_SOURCE_ABSENT`,
  `META_VERIFIED_AT_ABSENT`, `META_VERIFIED_AT_UNDATED` (value does not begin
  `YYYY-MM-DD`), `META_RECHECK_ABSENT` — warn; `META_RECHECK_UNSCHEDULED` (first
  token not an ISO date, `<N>d` or `on-release`) and `META_RECHECK_ROOT_PARENT`
  (the value passes `--root ..`) — info, drift only under `CHOUSA_STRICT=1`;
  `META_ENTRY_REFUSED` crit for an entry that is denylisted (raw or canonical
  path) or over 8 MiB (refused unread), or NUL-bearing (read for the NUL probe,
  refused unparsed) — all still counted in N/M.
  The refusal is a post-registration hardening from the round-25 sentinel seat
  (`.ufo/waves/round-25/build/SentinelMetaPaths.md`), disclosed here; it does
  not change the population result.
- Output: one `META entry=… source=… verified_at=… recheck=… verdict=…` line
  per entry, the findings, `METADATA_COMPLETE=N/M`, one `RESEARCH_GATE:` line;
  exit 0 / 1 / 2 (no path, missing path, directory without `.md`).
- Not composed into `verify-all`; the `--pin`/`--drift` canonical invocation is
  unchanged (`GATE_DRIFT: none` vs the r12 baseline at the landing).

# A due date schedules assessment, not truth

## Source-grounded distinction

Cochrane says its reviews should be assessed periodically to decide whether
an update is needed (S029, IV.1). Its LSR guidance distinguishes searching
from publishing updates and allows a fixed-interval update schedule in the
specified setting (S037, §4.3.4). Neither source prescribes generic research
note fields or a universal90-day cadence.

The following is **this lane's policy**, not a Cochrane rule [INFERENCE]:
use an entry's declared schedule to compute when an assessment is due.
Python's `date`/`timedelta` arithmetic represents the proleptic Gregorian
calendar and addition of calendar days (S038); the independent oracle uses
those semantics. Adopting them for the Bash checker is a lane design choice.

## Decision table

| recheck first token | verified-at | due | freshness at explicit as-of |
|---|---|---|---|
| calendar-validYYYY-MM-DD | any | explicit recheck date | overdue iff as-of>due, otherwise current |
| Nd (decimal calendar days) | valid leading ISO date | verified-at+N days | same strict comparison; equality is current |
| on-release | any | on-release | event; no inferred calendar deadline |
| command-only, absent, invalid, or out-of-range result | any | unknown | unknown, never silently current |

`--as-of` is opt-in. Without it the metadata screen retains its old output.
The new warning `META_RECHECK_OVERDUE` means the **declared schedule** passed;
it is not a finding that the entry is false. `freshness=current` means only
that the recorded deadline has not passed, not that sources were reopened.
`event` does not certify that releases were monitored. Unknown is honest
missing scheduling information; command-only legacy rechecks stay unknown.

## Recheck method

At a real due point, open the source and named anchor again, compare the
claim with what the source states, and record what was checked. A date alone
is not the re-verification (QUALITY6/8). Do not change a cadence solely to
turn an overdue report green. The frozen29 distribution and controls are
owned by the final measurement receipt; no row-count increase is asserted
as expanded domain understanding by itself.

# Search transparency — what a search record must report and how to record its sources (round 84)

source: S214, S018, S023

## What this entry governs

The lane's method searches sources, captures them, and registers what was found (`PROTOCOL.md` §4–§6). Held entries
say how a query is built (`search-query-exposure-r51.md`, `search-query-templates-r54.md`) and how a search log records
each attempt (`search-log-method-r39.md`, `search-tracking-record-r40.md`); none says what a *report of the search itself*
must contain so that a reader can audit it. PRISMA 2020's checklist states the reporting items for systematic-review
searches; a 2026 survey of evidence-based text generation states why linking output to supporting evidence matters; and
DCMI's metadata terms define the properties a record can use to name its source and its dates. The rows below keep only
what each quote states about reporting a search and recording its provenance; the checklist items for other review
sections are not taken.

## Decision table

| Situation | Do | Never | Warrant |
|---|---|---|---|
| Reporting which sources were searched | name every database, register, website, organisation, reference list, and other source consulted | report only the sources that returned results and omit those that returned none | Q1 (S214) |
| Reporting when a source was searched | state the date each source was last searched or consulted | report the search without dating it, so the reader cannot tell how current it is | Q2 (S214) |
| Reporting the search method | present the full search strategy for each source, including filters and limits | summarize the strategy in prose when the full strategy can be stated | Q3 (S214) |
| Reporting how studies were selected | state the methods used to decide whether a study met the inclusion criteria | report the selected studies without the selection method | Q4 (S214) |
| Reporting the search outcome | describe the results from records identified to studies included, ideally with a flow diagram | report only the final count without the identification-to-inclusion path | Q5 (S214) |
| Linking a claim to its source | cite, attribute, or quote the supporting evidence so the link is traceable | assert a claim without linking it to the evidence that supports it | Q6, Q7 (S018) |
| Comparing evidence-based generation approaches | use a shared taxonomy and unified benchmarks rather than isolated evaluation practices | compare approaches that use different terminologies and metrics without noting the fragmentation | Q8 (S018) |
| Recording what a resource derives from | name the related resource from which the described resource is derived | record a resource without naming its source | Q9 (S023) |
| Recording when a resource changed | state the date on which the resource was changed | record a modification without its date | Q10 (S023) |
| Recording when a resource is valid | state the date or range of validity of the resource | record a validity period without its dates | Q11 (S023) |
| Recording when a resource became available | state the date the resource became or will become available | record availability without its date | Q12 (S023) |

## Inference (lane's, not stated by the sources)

For this lane a "search record" is a committed search log or report (`corpus/logs/`), a "source" is a registry row
(`SOURCES.md`), and a "claim" is a lane claim or entry row. Read that way, the rows describe practice the lane already
runs in part — searches are logged with query and result (`search-log-method-r39.md`), sources are registered with
status and dates (`SOURCES.md`), and claims cite `S-ids` and `Q-ids` (`claims.md`, entry decision tables). The sources
state none of this mapping; it is the lane's reading, to be tested by future rounds.

## Limits

- PRISMA 2020 is written for systematic reviews of intervention studies; the checklist items govern review reporting,
  not general web search. The rows keep only the search-transparency items (6, 7, 8, 16a); eligibility criteria,
  risk-of-bias, synthesis, and reporting-bias items are not taken.
- The S018 survey is about evidence-based text generation with LLMs, not systematic reviews; its taxonomy and metrics
  are for model evaluation, not for search reporting. The rows keep only the attribution/traceability motivation.
- DCMI's terms are general metadata properties; they define what `source`, `modified`, `valid`, and `available` mean,
  not when or how often to set them. The rows keep only the definitions; no freshness or verification policy is implied.
- Row 8's Never assumes the related resource can be named; when the source is unknown or unavailable, the row does not
  apply.

# Correction and retraction status of a cited work — check it before reuse (round 81)

source: S205, S206, S207, S028
verified-at: 2026-11-06 (round 81; captures `371c55117727d526805f030d`, `f221c90f69188f775e32cd34`, `43a45b49723f7677d6446c92`)

## What this entry governs

The lane's claim check runs claim → source → the source's own evidence. A source that has since been corrected,
retracted or flagged with an expression of concern can still open, stay on topic and state the claim at a named
anchor — every one of the four support states in `corpus/knowledge/claim-support-states-r24.md` — while no longer
standing behind it. This entry adds the status check that has to precede reuse, read from three primary
descriptions of how that status is published.

## How the status is published (observations)

NLM (PubMed) links notices to the article they concern, in both directions. For an erratum that corrects a part of
the article not carried in the NLM citation (text, graphs, tables):

> "the erratum notice is simply linked to the citation for the corrected article." — S205

> "The Publication Type Retracted Publication [PT] is assigned to the retracted article." — S205

ICMJE asks journals to keep the version trail readable:

> "The journal should archive all prior versions of the article." — S206

> "Previous electronic versions should prominently note that there are more recent versions of the article" — S206

> "The citation should be to the most recent version." — S206

Crossref distributes the Retraction Watch database, with a stated coverage limit:

> "Some other update types, such as expressions of concern and corrections, are also included in the data, but these are not as comprehensive as retractions." — S207

## Decision table

| Observation about a cited work | Reading | Do | Never |
|---|---|---|---|
| PubMed record carries Publication Type Retracted Publication | retracted (S205) | record the claim's support as withdrawn; cite the retraction notice beside the work | count the work as support because the anchor still opens |
| PubMed record links an erratum notice | corrected (S205) | open the erratum and re-check the quoted span against the corrected text | quote the uncorrected wording as current |
| A newer article version exists (journal's version note) | the read wording may be superseded (S206) | cite the most recent version and re-check the quoted span against it; if only an earlier version was read, say which and that a newer one exists | cite an earlier version as current, or a version-less "the article says" |
| Retraction Watch data show no retraction | absence of a retraction record only (S207) | record the check (source, date) as a negative sweep | read it as "no correction or expression of concern either" — S207 says those types are less comprehensive |
| The notice cannot be read (host refuses the fetch) | status unknown | keep the source, mark the status check unresolved, name the notice | treat unreachable as "no notice" |

The last row is this round's own case: the TARCiS correction BMJ 2024;387:q2458 answered HTTP 403 (S208, rejected,
unreachable) — `corpus/knowledge/citation-searching-tarcis-r81.md` records the consequence.

## Inference (lane's, not stated by the sources)

A status check is a negative claim ("no retraction found"), so under this lane's checklist it carries a sweep naming
where it looked (PubMed publication types and linked notices, the journal's version note, the Retraction Watch data)
and the date it looked. The three sources describe where status is published; none of them states this checklist rule.

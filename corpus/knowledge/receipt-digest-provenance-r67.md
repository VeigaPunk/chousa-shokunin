# A receipt digest is evidence only when it re-derives from committed bytes

## Claims

1. S161 states the canonical identity semantics git's receipts rest on: the tool "Computes the object ID value for an object with specified type with the contents of the named file" — identity follows content, so a digest pin in a receipt is a promise that specific bytes are committed — and S161 also scopes the promise: "The location of the file does not directly influence the hash value, but the path is used to determine which Git filters should be applied", so a receipt digest must be computed over blob bytes as stored (`git cat-file`), never over working-tree bytes that a filter (line-ending conversion, clean/smudge) may transform.
2. S162 is the recorded counterexample class: a before-receipt whose `ENTRY_SHA256` (`c0aaa9ed…`) and `REGISTRY_SHA256` (`b19f9ac6…`) match no blob among all 14,869 objects of the lane repository (`tools/digest-in-tree.py --all-objects` → `DIGESTS_IN_TREE=0/2`, each named `OUT_OF_TREE`) — bytes from a scratch clone that never entered any commit, so no reader could re-derive them and the measurement was unverifiable in principle; the claim it carried was repaired only by a later committed-fixture receipt (`corpus/evidence/round67/controls/before-r66-counter-committed-fixture.txt`, digests `bca84fad…`/`113ea182…`, both IN_TREE).
3. Inference: the provenance rule for every receipt is — pin only digests of bytes committed at the revision the receipt names (a committed fixture, not a scratch clone; commit the fixture first, then receipt it), let a checker fail any pin that re-derives from nothing (`DIGESTS_IN_TREE=0/n` with the named reason `OUT_OF_TREE`), stay fail-closed when nothing is pinned (exit 2 `NO_DIGESTS`; revision binding for digest-free receipts remains `tools/receipt-pin.py`'s contract), and treat a pass as re-derivability only — the reader can reproduce the bytes from the repository alone.

## Limits

Re-derivability is provenance, not truth: a digest that re-derives proves the bytes are committed, not which command produced them, that the recorded run happened, or that the claim is entailed (support state 3 only, QUALITY criterion 8; entailment stays with the non-author reviewer, the QUALITY-131 residual). The rev mode scans blobs reachable at the named revision only, so a digest from an earlier revision verifies only against that revision or with `--all-objects`; the all-objects mode (history plus unreachable objects) is the stronger statement and is what the S162 verdict cites.

One repository, one digest algorithm, one point in time: sha256 over git blob bytes at 2026-10-31; a receipt quoting a foreign digest (sha1, blake2, a hash of a path string) is not a 64-hex sha256 pin and is refused as `NO_DIGESTS`, which is fail-closed, not evidence that provenance exists; and the corrected-fixture receipt re-measures the r66 before-state, it does not rewrite the defective receipt — history stays append-only, the defect stays named at `corpus/evidence/round66/controls/before-new-counter-boilerplate.txt`.

## Use in research

Before citing a receipt's digest, re-derive it from the revision the receipt names (`tools/digest-in-tree.py --receipt FILE --revision REV`, or `--all-objects` for the repository-wide statement); before writing a receipt, generate every digest it pins from bytes that are already committed. When a receipt is found un-derivable, name it `OUT_OF_TREE` in a correction note — never quietly replace the pinned value — and re-issue the measurement from committed fixture bytes as a new receipt that names the old one, as `before-r66-counter-committed-fixture.txt` does for S162.
